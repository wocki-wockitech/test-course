# PHP: ООП, SOLID и паттерны

Этот урок — про то, как объяснять архитектурные решения словами. На собесе
важнее не вызубрить определения, а уметь сказать «почему так». Пройдём ООП в
PHP, принципы SOLID и самые ходовые паттерны.

## ООП в PHP: что важно помнить

- **Интерфейсы** описывают контракт, **абстрактные классы** — частичную
  реализацию. Класс реализует много интерфейсов, но наследует один класс.
- **Трейты** (`trait`) — горизонтальное переиспользование кода без наследования.
  Решают «алмаз смерти» отсутствием множественного наследования.
- **Видимость**: `public`, `protected`, `private`.
- **`final`** запрещает наследование/переопределение — полезно для защиты
  инварианта.
- **Late static binding** (`static::`) — вызов разрешается по реальному классу
  в рантайме, в отличие от `self::`, который привязан к месту объявления.

```php
abstract class Repository
{
    public static function create(): static
    {
        return new static(); // вернёт конкретный подкласс
    }
}
```

## DI и инверсия зависимостей

**Dependency Injection** — зависимости передаются снаружи (через конструктор),
а не создаются внутри класса. Это упрощает тесты (можно подсунуть мок) и
снижает связанность.

```php
final class OrderService
{
    public function __construct(
        private PaymentGateway $gateway,   // зависимость инжектится
        private OrderRepository $orders,
    ) {}
}
```

**DI-контейнер** автоматически собирает граф зависимостей. Не путай:
DI — это паттерн, контейнер — инструмент.

## SOLID простыми словами

- **S — Single Responsibility**: у класса одна причина для изменения. Не
  смешивай парсинг, бизнес-логику и запись в БД в одном классе.
- **O — Open/Closed**: открыт для расширения, закрыт для изменения. Добавляешь
  новое поведение через новый класс/стратегию, а не правкой существующего.
- **L — Liskov Substitution**: подкласс можно подставить вместо родителя, не
  ломая поведение. Если `Square extends Rectangle` ломает логику — это нарушение.
- **I — Interface Segregation**: лучше несколько узких интерфейсов, чем один
  «толстый». Клиент не должен зависеть от методов, которые не использует.
- **D — Dependency Inversion**: зависим от абстракций, а не от конкретики.
  Высокоуровневый код не должен знать про конкретную реализацию БД.

> [!tip] Как отвечать про SOLID
> Не перечисляй определения наизусть. Дай букву, одну фразу сути и короткий
> пример нарушения. Это звучит как опыт, а не зубрёжка.

## Ходовые паттерны

- **Strategy** — взаимозаменяемые алгоритмы за общим интерфейсом (разные
  способы оплаты, разные форматы экспорта).
- **Factory** — инкапсулирует создание объектов.
- **Repository** — абстракция доступа к данным, прячет источник (БД, API).
- **Decorator** — оборачивает объект, добавляя поведение (например, кеширующий
  декоратор поверх репозитория).
- **Observer** — подписка на события (event dispatcher).
- **Adapter** — приводит несовместимый интерфейс к нужному.

```php
interface Exporter { public function export(array $data): string; }

final class CsvExporter implements Exporter { /* ... */ }
final class JsonExporter implements Exporter { /* ... */ }

// Strategy: подменяем реализацию, не трогая клиента
function report(Exporter $e, array $data): string {
    return $e->export($data);
}
```

## PSR — стандарты, которые ждут на собесе

- **PSR-4** — автозагрузка по неймспейсам (Composer).
- **PSR-7** — HTTP-сообщения (Request/Response интерфейсы).
- **PSR-11** — интерфейс DI-контейнера.
- **PSR-12** — стиль кода.
- **PSR-3** — интерфейс логгера.

## Итог

- Интерфейс = контракт, абстрактный класс = частичная реализация, трейт =
  переиспользование без наследования.
- DI снижает связанность и упрощает тесты; контейнер собирает граф.
- SOLID объясняй через примеры нарушений, а не определения.
- Знай Strategy, Factory, Repository, Decorator и базовые PSR.
