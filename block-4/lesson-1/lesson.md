# Redis и кеширование

Цель урока — закрыть базу про Redis и кеширование, которую почти всегда
спрашивают на бэкенд-собесе: что такое Redis, какие структуры данных он даёт,
как работают TTL и персистентность, какие есть паттерны кеширования и как
бороться с типичными проблемами вроде cache stampede. Простым языком, с
прицелом на устные ответы.

## Что такое Redis

Redis (REmote DIctionary Server) — это **in-memory key-value хранилище**. Все
данные лежат в оперативной памяти, поэтому операции выполняются за
микросекунды. Redis однопоточный по обработке команд (одна команда за раз,
атомарно), что убирает гонки и блокировки на уровне логики.

Где используют:
- **кеш** перед БД (самый частый сценарий);
- **хранилище сессий**;
- **брокер сообщений** / очередь (списки, Pub/Sub, Streams);
- **распределённые блокировки** и счётчики;
- **rate limiting**, лидерборды, аналитика реального времени.

> [!tip] Что сказать на собесе
> «Redis — это in-memory key-value стор. Данные в RAM, поэтому быстрый.
> Однопоточный по командам, каждая команда атомарна. Использую как кеш,
> хранилище сессий, брокер и для распределённых локов.»

## Структуры данных

Redis — не просто «ключ → строка». Значения бывают разных типов, и под задачу
выбирают подходящий:

- **String** — строка/число. Кеш JSON, счётчики (`INCR`), флаги.
- **Hash** — словарь полей внутри ключа. Объект целиком: `user:1 → {name, age}`.
- **List** — связанный список. Очереди (`LPUSH`/`RPOP`), последние N событий.
- **Set** — множество уникальных значений. Теги, уникальные посетители,
  пересечения (`SINTER`).
- **Sorted Set (ZSet)** — множество с числовым score. Лидерборды, очереди с
  приоритетом, выборки по диапазону (`ZRANGEBYSCORE`).

Есть и специальные: **Bitmap**, **HyperLogLog** (примерный подсчёт уникальных),
**Geo**, **Streams** (журнал событий с consumer-группами).

```bash
SET user:1:name "Alice"          # string
HSET user:1 name Alice age 30    # hash
LPUSH queue:jobs "job1"          # list
SADD tags:php "redis" "cache"    # set
ZADD leaderboard 100 alice       # sorted set
```

## TTL и истечение ключей

Любому ключу можно задать время жизни — после него ключ автоматически удаляется.
Это основа кеша.

```bash
SET session:abc "data" EX 3600   # живёт 3600 секунд
EXPIRE user:1 600                # задать TTL отдельной командой
TTL user:1                       # сколько осталось (сек), -1 без TTL, -2 нет ключа
PERSIST user:1                   # снять TTL
```

Удаление по TTL работает двумя способами: **lazy** (ключ проверяется при
обращении) и **active** (фоновый процесс периодически чистит протухшие ключи).

> [!warning] Грабли
> `SET key value` без указания TTL **сбрасывает** ранее установленный expire.
> Если нужно сохранить TTL — используй `SET ... KEEPTTL` или `EXPIRE` отдельно.

## Персистентность: RDB vs AOF

Redis в памяти, но умеет сохранять данные на диск, чтобы пережить рестарт.

- **RDB (snapshot)** — периодический бинарный снимок всего датасета. Компактный,
  быстро грузится, но при падении теряются изменения с момента последнего снимка.
- **AOF (Append Only File)** — журнал всех команд на запись. Меньше потерь
  (можно `fsync` каждую секунду или каждую команду), но файл больше и
  восстановление медленнее.

На практике часто включают **оба**: AOF для надёжности + RDB для быстрого
старта и бэкапов.

> [!tip] Что сказать на собесе
> «RDB — снапшоты, компактно и быстро грузится, но можно потерять последние
> секунды. AOF — лог команд, меньше потерь, но файл больше. Для кеша
> персистентность часто вообще не нужна; для важных данных включаю AOF.»

## Паттерны кеширования

Как именно приложение работает с кешем поверх БД:

- **Cache-aside (lazy loading)** — приложение само управляет кешем: читает из
  кеша, при промахе идёт в БД и кладёт результат в кеш. Самый распространённый.
- **Read-through** — приложение всегда читает через кеш; кеш сам подтягивает
  данные из БД при промахе (логика в слое кеша).
- **Write-through** — запись идёт в кеш и сразу синхронно в БД. Данные всегда
  свежие в кеше, но запись медленнее.
- **Write-behind (write-back)** — запись в кеш, а в БД асинхронно позже. Быстрая
  запись, но риск потерять данные при падении до сброса.

```text
Cache-aside (чтение):
  data = cache.get(key)
  if data is None:          # промах
      data = db.query(key)
      cache.set(key, data, ttl=300)
  return data
```

## Инвалидация кеша

«В программировании две сложные вещи: инвалидация кеша и именование». Способы:
- **TTL** — самый простой, кеш сам протухает через время. Допускает временную
  рассинхронизацию.
- **Явное удаление/обновление** при изменении данных (`DEL key` после `UPDATE`).
- **Версионирование ключа** — менять ключ при изменении схемы/данных
  (`user:1:v2`).

> [!tip] Что сказать на собесе
> «По умолчанию ставлю TTL, а на изменения данных делаю явную инвалидацию
> (удаляю или перезаписываю ключ). Полностью консистентный кеш — дорого, обычно
> допускаю небольшую устаревшесть.»

## Cache stampede (промах под нагрузкой)

**Cache stampede** (он же thundering herd) — когда популярный ключ протухает, и
сразу множество запросов обнаруживают промах и одновременно бьют в БД,
перегружая её.

Способы борьбы:
- **Блокировка/мьютекс** — только один запрос пересчитывает значение
  (через `SETNX`-лок), остальные ждут или отдают старое.
- **Early recomputation** — обновлять значение чуть раньше истечения TTL
  (вероятностно).
- **Stale-while-revalidate** — отдавать устаревшее значение, пока в фоне идёт
  пересчёт.
- **Jitter** — разбрасывать TTL случайным разбросом, чтобы ключи не протухали
  одновременно.

## Распределённый лок через SETNX

Redis часто используют для распределённой блокировки между инстансами:

```bash
SET lock:resource token NX EX 30   # захватить лок, только если нет, на 30с
# ... критическая секция ...
# освобождение — атомарно через Lua, сверяя token, чтобы не снять чужой лок
```

- `NX` — поставить ключ, только если его нет (атомарный захват).
- `EX 30` — авто-освобождение, чтобы лок не завис навсегда при падении владельца.
- Снятие проверяет токен (через Lua-скрипт), чтобы не удалить лок, который уже
  перехватил другой. Для строгих гарантий есть алгоритм **Redlock**.

## Redis vs Memcached

Частый вопрос на сравнение:

- **Memcached** — простой кеш: только строки, многопоточный, отлично шардируется
  для чистого кеширования больших объёмов.
- **Redis** — богатые структуры данных, персистентность, репликация, Pub/Sub,
  скрипты, транзакции. Универсальнее.

Если нужен просто быстрый кеш строк — подойдёт оба; если нужны структуры,
персистентность или брокер — Redis.

## Eviction policy

Когда память заполнена (`maxmemory`), Redis вытесняет ключи по политике:

- **noeviction** — отдаёт ошибку на запись (по умолчанию).
- **allkeys-lru** — вытесняет давно не используемые из всех ключей.
- **volatile-lru** — то же, но только среди ключей с TTL.
- **allkeys-lfu / volatile-lfu** — по частоте использования (LFU).
- **volatile-ttl** — вытесняет с ближайшим истечением.
- **allkeys-random / volatile-random** — случайно.

Для чистого кеша обычно ставят `allkeys-lru` или `allkeys-lfu`.

## Итог

- Redis — in-memory key-value стор, однопоточный по командам, очень быстрый.
- Структуры: string, hash, list, set, sorted set (+ bitmap, HLL, streams).
- TTL/EXPIRE — основа кеша; `SET` без `KEEPTTL` сбрасывает expire.
- Персистентность: RDB (снапшоты) vs AOF (лог команд), часто оба.
- Паттерны: cache-aside, read-through, write-through, write-behind.
- Инвалидация — TTL + явное удаление; cache stampede лечат локом/jitter/SWR.
- SETNX NX EX — распределённый лок; eviction обычно allkeys-lru/lfu.
