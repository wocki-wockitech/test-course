# gRPC и Protobuf

Цель урока — понять, что такое gRPC, чем он отличается от REST, какие бывают
типы вызовов, как устроена protobuf-схема и её обратная совместимость, и когда
выбирать gRPC, а когда REST.

## Что такое gRPC

**gRPC** — это фреймворк удалённого вызова процедур (RPC) от Google. Два кита:

- **Транспорт — HTTP/2**: мультиплексирование (много запросов в одном
  соединении), бинарные фреймы, сжатие заголовков, стриминг.
- **Сериализация — Protocol Buffers (protobuf)**: компактный бинарный формат и
  строгая схема в `.proto`-файле.

Из схемы кодогенератор делает клиент и сервер на разных языках (Go, PHP, и т.д.).
Контракт описан в одном месте и типобезопасен.

> [!tip] Что сказать на собесе
> «gRPC — RPC поверх HTTP/2 с protobuf. Бинарный компактный формат, строгий
> контракт из .proto, кодогенерация клиента/сервера, поддержка стриминга.»

## gRPC vs REST

| | REST (JSON/HTTP) | gRPC |
|---|---|---|
| Транспорт | HTTP/1.1 или 2 | HTTP/2 |
| Формат | текст (JSON) | бинарный (protobuf) |
| Контракт | OpenAPI (опционально) | .proto (строгий) |
| Стриминг | ограниченно | из коробки (4 типа) |
| Браузер | напрямую | нужен grpc-web/прокси |
| Читаемость | человекочитаемо | нужен инструмент |

gRPC обычно быстрее и компактнее за счёт бинарной сериализации и HTTP/2, но
менее удобен для отладки руками и не работает напрямую из браузера.

## Типы вызовов

protobuf/gRPC поддерживает четыре вида методов:

- **Unary** — один запрос, один ответ (как обычный вызов функции).
- **Server streaming** — один запрос, поток ответов (лента, подписка).
- **Client streaming** — поток запросов, один ответ (загрузка кусками).
- **Bidirectional streaming** — оба стримят одновременно (чат, реалтайм).

Стриминг работает поверх одного HTTP/2-соединения.

## Protobuf-схема

Сервис и сообщения описываются в `.proto`. У каждого поля — имя, тип и
**номер (тег)**. В бинарном формате передаётся именно номер поля, а не имя.

```proto
syntax = "proto3";

message User {
  int64 id = 1;
  string email = 2;
  string name = 3;
}

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
```

В proto3 поля по умолчанию опциональны и имеют «нулевые» значения по умолчанию
(0, "", false), отдельного «required» нет — это сделано как раз ради эволюции
схемы.

## Обратная совместимость

Главное правило — **номера полей вечны**. На них завязана бинарная
сериализация. Что безопасно, а что ломает совместимость:

- **Безопасно**: добавить новое поле с новым номером; старые клиенты его не
  увидят, новые прочитают.
- **Безопасно**: перестать использовать поле — но номер не переиспользовать
  (пометь `reserved`).
- **Ломает**: переиспользовать номер удалённого поля под другое поле/тип —
  старые данные «прочитаются» как мусор.
- **Ломает**: менять номер существующего поля или несовместимо менять его тип.
- Переименование поля само по себе безопасно для бинарного формата (имя не
  передаётся), но ломает текстовые представления и кодогенерированный код.

> [!warning] reserved
> Удаляя поле, резервируй его номер и имя: `reserved 2; reserved "email";`.
> Это запрещает случайно переиспользовать их и сломать старых клиентов.

## Когда gRPC, а когда REST

- **gRPC** — внутренняя коммуникация между сервисами, низкая задержка, высокий
  RPS, стриминг, строгий контракт и кодогенерация на многих языках.
- **REST/JSON** — публичные API, прямой доступ из браузера, простая отладка,
  широкая совместимость с инструментами и кешированием.

Часто их совмещают: gRPC внутри, REST наружу (или через gRPC-gateway).

## Итог

- gRPC — RPC поверх HTTP/2 с бинарным protobuf и строгим .proto-контрактом.
- 4 типа вызовов: unary, server/client/bidirectional streaming.
- Номера полей в protobuf неизменны; новые поля — новые номера, удалённые —
  `reserved`. Переиспользование номера ломает совместимость.
- gRPC хорош внутри (скорость, стриминг, контракт), REST — наружу (браузер,
  отладка, совместимость).
