# REST API

Цель урока — собрать базу по REST, которую почти всегда спрашивают: принципы,
HTTP-методы и их свойства, статус-коды, идемпотентность, версионирование,
пагинация, отличие от RPC и роль OpenAPI/Swagger.

## Принципы REST

**REST** — это архитектурный стиль поверх HTTP, а не протокол. Основные идеи:

- **Ресурсы** адресуются URI: `/users/42`, `/orders/7/items`. Существительные,
  не глаголы (плохо: `/getUser`, хорошо: `GET /users/42`).
- **Stateless**: сервер не хранит состояние клиента между запросами; каждый
  запрос самодостаточен (авторизация передаётся каждый раз).
- **Единый интерфейс**: операции выражаются HTTP-методами над ресурсами.
- **Представления**: один ресурс может отдаваться в разных форматах (обычно
  JSON).

> [!tip] Что сказать на собесе
> «REST — стиль поверх HTTP: ресурсы в URI, операции через HTTP-методы,
> stateless-сервер, понятные статус-коды. Глаголы — это методы, не путь.»

## HTTP-методы: безопасность и идемпотентность

- **Безопасный** метод не меняет состояние на сервере (только чтение).
- **Идемпотентный** метод можно повторить — результат на сервере тот же.

| Метод | Назначение | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | чтение | да | да |
| POST | создание | нет | нет |
| PUT | полная замена/создание по id | нет | да |
| PATCH | частичное обновление | нет | обычно нет |
| DELETE | удаление | нет | да |

`PUT` идемпотентен, потому что повторная отправка того же тела даёт то же
состояние ресурса. `POST` создаёт новый ресурс каждый раз, поэтому не
идемпотентен. `DELETE` идемпотентен по состоянию: ресурс удалён и остаётся
удалённым (хотя второй вызов может вернуть 404).

## Статус-коды

Группы: **2xx** успех, **3xx** редирект, **4xx** ошибка клиента, **5xx** ошибка
сервера. Конкретику стоит знать наизусть:

- **200 OK** — успешный GET/PUT/PATCH с телом ответа.
- **201 Created** — ресурс создан (обычно ответ на POST, с заголовком `Location`).
- **204 No Content** — успех без тела (часто DELETE или PUT без возврата).
- **400 Bad Request** — некорректный запрос (битый JSON, неверный формат).
- **401 Unauthorized** — не аутентифицирован (нет/невалидный токен).
- **403 Forbidden** — аутентифицирован, но нет прав.
- **404 Not Found** — ресурс не найден.
- **409 Conflict** — конфликт состояния (дубликат, конкурентное изменение).
- **422 Unprocessable Entity** — синтаксис ок, но валидация бизнес-правил не прошла.
- **429 Too Many Requests** — превышен rate limit.
- **500 Internal Server Error** — необработанная ошибка на сервере.
- **503 Service Unavailable** — сервис временно недоступен (перегрузка, деплой).

> [!warning] 401 vs 403
> 401 — «я не знаю, кто ты» (нет валидной аутентификации). 403 — «я знаю, кто
> ты, но тебе нельзя». Частый вопрос на собесе.

## Идемпотентность на практике

Чтобы безопасно повторять POST (например, при ретрае платежа), клиент шлёт
заголовок `Idempotency-Key`. Сервер запоминает ключ и при повторе возвращает
тот же результат, не создавая дубль. Это превращает не идемпотентную операцию
в безопасную для ретраев.

## Версионирование API

API меняется, а старые клиенты должны продолжать работать. Подходы:

- **В пути**: `/v1/users`, `/v2/users` — самый явный и популярный.
- **В заголовке**: `Accept: application/vnd.api.v2+json`.
- **В query**: `/users?version=2` — реже.

Главное правило — **не ломать обратную совместимость** в рамках одной версии:
не удалять поля, не менять их смысл, новые поля делать опциональными.

## Пагинация

Большие коллекции нельзя отдавать целиком. Варианты:

- **Offset/limit**: `?limit=20&offset=40` — просто, но дорого на больших
  смещениях и «съезжает» при вставках.
- **Cursor/keyset**: `?limit=20&after=<cursor>` — стабильнее и быстрее на
  больших данных, курсор указывает на позицию.

## REST vs RPC

REST мыслит **ресурсами** и стандартными методами. **RPC** мыслит **действиями
(вызовами процедур)**: `createUser`, `chargeCard`. RPC удобен для команд, которые
плохо ложатся на CRUD-ресурсы. gRPC — это RPC поверх HTTP/2 (следующий урок).
На практике многие API — гибрид: REST для ресурсов, отдельные «action»-эндпоинты
для операций.

## Swagger / OpenAPI

**OpenAPI** — стандарт описания REST API в машиночитаемом виде (YAML/JSON):
пути, методы, схемы запросов/ответов, коды. **Swagger UI** рендерит из этого
интерактивную документацию. Польза: единый контракт, автогенерация клиентов и
серверных заготовок, валидация.

## Итог

- REST — стиль поверх HTTP: ресурсы в URI, операции через методы, stateless.
- GET/PUT/DELETE идемпотентны, POST — нет; GET ещё и безопасный.
- Знай коды: 200/201/204, 400/401/403/404/409/422/429, 500/503.
- Идемпотентность POST решается ключом `Idempotency-Key`.
- Версионируй (часто `/v1/`), не ломай совместимость, пагинируй коллекции.
- OpenAPI/Swagger — контракт и документация API.
