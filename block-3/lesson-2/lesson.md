# Индексы и оптимизация запросов

Цель урока — разобраться, как работают индексы, когда они не применяются, что
такое правило левого префикса и покрывающий индекс, как читать `EXPLAIN` и чем
seq scan отличается от index scan. И почему индексы — это не «добавить везде»,
а компромисс между скоростью чтения и стоимостью записи. С прицелом на устные
ответы.

## Что такое индекс

Индекс — это отдельная структура данных, которая хранит значения колонки в
упорядоченном виде и указывает на строки таблицы. Чаще всего это **B-tree**
(сбалансированное дерево): поиск, диапазоны и сортировка работают за
`O(log n)` вместо полного перебора.

Без индекса БД делает **seq scan** — читает всю таблицу. С подходящим индексом —
**index scan** — спускается по дереву к нужным строкам.

> [!tip] Что сказать на собесе
> «Индекс — это упорядоченная структура (обычно B-tree), которая ускоряет
> поиск и диапазонные запросы ценой замедления записи и доп. места на диске.»

## Когда индекс НЕ работает

Очень частый вопрос. Индекс по колонке не применится, если:

- **Функция/выражение над колонкой**: `WHERE LOWER(email) = 'a@b.c'` — индекс по
  `email` бесполезен (нужен функциональный индекс по `LOWER(email)`).
- **Leading wildcard в LIKE**: `WHERE name LIKE '%abc'` — префикс неизвестен,
  B-tree не помогает. А `LIKE 'abc%'` — отработает.
- **Приведение типов**: сравнение колонки одного типа с константой другого.
- **Низкая селективность**: если значение встречается в половине строк,
  планировщик сам выберет seq scan — это дешевле.

```sql
-- Индекс по email НЕ применится: функция над колонкой
SELECT * FROM users WHERE LOWER(email) = 'a@b.c';

-- Применится функциональный индекс:
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
```

## Составные индексы и правило левого префикса

Составной индекс `(a, b, c)` упорядочен сначала по `a`, потом по `b`, потом по
`c`. Поэтому он работает только если запрос использует **левый префикс**:

- `WHERE a = ?` — работает.
- `WHERE a = ? AND b = ?` — работает.
- `WHERE a = ? AND b = ? AND c = ?` — работает.
- `WHERE b = ?` (без `a`) — **не работает** как индексный поиск.
- `WHERE a = ? AND c = ?` — использует только часть по `a`.

> [!tip] Что сказать на собесе
> «Составной индекс — это упорядоченный кортеж. Запрос должен идти слева
> направо: без первого столбца индекс не используется для поиска. Порядок
> столбцов в индексе важен.»

## Покрывающий индекс

**Покрывающий индекс (covering index)** содержит все колонки, которые нужны
запросу, поэтому БД отвечает прямо из индекса, не заглядывая в таблицу
(index-only scan).

```sql
-- Запросу нужны только user_id и created_at
CREATE INDEX idx_orders_cover ON orders (user_id, created_at);
SELECT created_at FROM orders WHERE user_id = 42;  -- index-only scan
```

В PostgreSQL можно добавить неключевые колонки через `INCLUDE`.

## EXPLAIN и EXPLAIN ANALYZE

- `EXPLAIN` — показывает **план** запроса (оценки планировщика), без выполнения.
- `EXPLAIN ANALYZE` — реально **выполняет** запрос и показывает фактическое
  время и число строк. На записывающих запросах оборачивай в транзакцию с
  откатом.

Что искать в плане:
- `Seq Scan` по большой таблице с фильтром — кандидат на индекс.
- `Index Scan` / `Index Only Scan` — индекс используется.
- Расхождение оценки (`rows=`) и факта (`actual rows=`) — устаревшая
  статистика, поможет `ANALYZE`.

> [!warning] Грабли
> `EXPLAIN ANALYZE` для `UPDATE`/`DELETE`/`INSERT` реально изменит данные.
> Запускай внутри `BEGIN; ... ROLLBACK;`.

## Проблема N+1

**N+1** — это когда вместо одного запроса с `JOIN`/`IN` приложение делает 1
запрос на список и ещё N запросов на каждую запись. Классика ORM при ленивой
загрузке связей.

Лечится eager-загрузкой (`JOIN`, `IN (...)`, `WITH`) или батчингом. На собесе
важно сказать: «N+1 — это про количество round-trip к БД, а не про сам SQL».

## Когда индекс вредит

Индекс ускоряет чтение, но:
- Замедляет **запись** (`INSERT`/`UPDATE`/`DELETE`) — индекс надо обновлять.
- Занимает место на диске и в памяти.
- Лишние и дублирующие индексы только нагружают планировщик и запись.

> [!tip] Правило
> Индексируй под реальные запросы (по `WHERE`, `JOIN`, `ORDER BY`), а не «на
> всякий случай». На write-heavy таблицах лишние индексы особенно дороги.

## Итог

- Индекс (B-tree) ускоряет поиск/диапазоны/сортировку ценой записи и места.
- Не работает при функции над колонкой, `LIKE '%x'`, приведении типов, низкой
  селективности.
- Составной индекс — правило левого префикса: порядок столбцов важен.
- Покрывающий индекс отвечает без обращения к таблице (index-only scan).
- `EXPLAIN` показывает план, `EXPLAIN ANALYZE` — факт; ищи Seq Scan по большим
  таблицам.
- N+1 — про число запросов к БД; лечится eager-загрузкой.
- Лишние индексы вредят записи — индексируй под реальные запросы.
