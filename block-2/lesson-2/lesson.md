# Go: конкурентность

Конкурентность — главная фича Go и самая частая тема на собесе. Разберём
goroutines, каналы (буферизованные и нет), `select`, примитивы синхронизации
(`Mutex`, `RWMutex`, `WaitGroup`), `context` для отмены и таймаутов, что такое
data race и deadlock, и как собрать worker pool. Простым языком, с прицелом
на устные ответы.

## Goroutines

Goroutine — это лёгкий поток выполнения, управляемый рантаймом Go, а не ОС.
Запускается словом `go`:

```go
go doWork() // запустили в фоне, main не ждёт
```

Стек горутины стартует с ~2 КБ и растёт по мере надобности, поэтому их можно
держать сотнями тысяч. Планировщик Go мультиплексирует множество горутин на
небольшое число системных потоков (об этом — в уроке про рантайм).

> [!warning] Грабли
> Если `main` завершится, все горутины умрут, не доделав работу. Поэтому
> нужно явно дожидаться их — через `WaitGroup` или каналы.

## Каналы: общение вместо разделяемой памяти

Идиома Go: **«Don't communicate by sharing memory; share memory by
communicating»**. Каналы — типизированные «трубы» для передачи значений
между горутинами.

```go
ch := make(chan int)     // небуферизованный
ch := make(chan int, 10) // буферизованный, ёмкость 10
```

- **Небуферизованный** канал синхронный: отправка блокируется, пока кто-то
  не примет; приём блокируется, пока кто-то не отправит. Это рандеву.
- **Буферизованный** канал: отправка блокируется только когда буфер полон,
  приём — когда буфер пуст.

```go
ch := make(chan int, 1)
ch <- 1      // не блокирует: в буфере есть место
v := <-ch    // приняли
close(ch)    // закрытие; читать из закрытого можно, писать — panic
```

Чтение из закрытого канала возвращает zero value и `ok == false`:

```go
v, ok := <-ch // ok == false, если канал закрыт и пуст
```

> [!important] Правила каналов
> - Закрывает канал **отправитель**, не получатель.
> - Запись в закрытый канал → panic.
> - Запись/чтение из nil-канала блокирует **навсегда**.

## select: ждём несколько каналов

`select` блокируется, пока не готова одна из веток; если готовы несколько —
выбирается случайная. `default` делает операцию неблокирующей.

```go
select {
case v := <-ch1:
    use(v)
case ch2 <- x:
    // отправили в ch2
case <-time.After(time.Second):
    // таймаут
default:
    // ничего не готово прямо сейчас
}
```

## Deadlock на небуферизованном канале

Самая частая ошибка новичка — отправить в небуферизованный канал, когда
никто не читает (или наоборот). Рантайм Go детектит, когда **все** горутины
заблокированы, и падает с `fatal error: all goroutines are asleep -
deadlock!`.

```go
ch := make(chan int) // небуферизованный
ch <- 1              // DEADLOCK: некому принять, main блокируется навсегда
```

## Примитивы синхронизации

Когда разделяемую память всё-таки используют, доступ защищают мьютексами.

- **`sync.Mutex`** — взаимное исключение: `Lock()` / `Unlock()`.
- **`sync.RWMutex`** — много читателей ИЛИ один писатель: `RLock()` для
  чтения, `Lock()` для записи. Полезен при «читают часто, пишут редко».
- **`sync.WaitGroup`** — дождаться завершения группы горутин.

```go
var mu sync.Mutex
mu.Lock()
counter++          // критическая секция
mu.Unlock()
```

```go
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        work()
    }()
}
wg.Wait() // блокируемся, пока счётчик не станет 0
```

> [!warning] Грабли WaitGroup
> `wg.Add(n)` вызывают **до** запуска горутины, а `defer wg.Done()` —
> первой строкой внутри. Если `Add` вызвать внутри горутины, `Wait` может
> проскочить раньше.

## Data race vs race condition

- **Data race** — два потока обращаются к одной памяти одновременно, и хотя
  бы один пишет, без синхронизации. Это неопределённое поведение.
- **Race condition** — более широкое понятие: результат зависит от
  относительного тайминга операций.

Запусти тесты с детектором гонок:

```bash
go test -race ./...
go run -race main.go
```

```go
// DATA RACE: несколько горутин пишут counter без блокировки
counter := 0
for i := 0; i < 1000; i++ {
    go func() { counter++ }() // counter++ не атомарна
}
```

Чинят мьютексом, каналом или `sync/atomic`.

## context: отмена и таймауты

`context.Context` пробрасывает сигнал отмены и дедлайны через цепочку
вызовов. Канонически — первый аргумент функции.

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel() // всегда вызываем cancel, чтобы не утекли ресурсы

select {
case <-ctx.Done():
    return ctx.Err() // context deadline exceeded или canceled
case res := <-resultCh:
    return res
}
```

- `WithCancel` — ручная отмена.
- `WithTimeout` / `WithDeadline` — отмена по времени.
- `ctx.Done()` — канал, который закрывается при отмене.

> [!tip] Что сказать на собесе
> «context — стандартный способ отмены и таймаутов. Передаю первым
> аргументом, всегда `defer cancel()`, а в долгих операциях слушаю
> `ctx.Done()`.»

## Паттерн worker pool

Ограничиваем число одновременных горутин: фиксированный пул воркеров читает
задачи из одного канала и пишет результаты в другой.

```go
jobs := make(chan int, 100)
results := make(chan int, 100)

// стартуем N воркеров
for w := 0; w < 3; w++ {
    go func() {
        for j := range jobs { // читаем, пока канал не закрыт
            results <- j * 2
        }
    }()
}

for i := 1; i <= 9; i++ {
    jobs <- i
}
close(jobs) // сигнал воркерам, что задач больше не будет
```

## Итог

- Goroutine — лёгкий поток рантайма; `main` не ждёт их без синхронизации.
- Небуферизованный канал синхронный (рандеву), буферизованный блокирует по
  заполнению/опустошению.
- Закрывает канал отправитель; запись в закрытый/nil канал — panic/вечная блокировка.
- Data race — несинхронизированный конкурентный доступ с записью; лови `-race`.
- context — отмена и таймауты, всегда `defer cancel()`, слушай `ctx.Done()`.
- Worker pool ограничивает конкурентность фиксированным числом воркеров.
