# Kubernetes

Цель урока — за 15 минут собрать в голове картину Kubernetes: зачем нужна
оркестрация, какие есть основные объекты, как Service находит поды, как работают
probes, масштабирование и rolling update. Простым языком, с прицелом на устные
ответы.

## Зачем оркестрация

Когда контейнеров много и они на нескольких машинах, вручную их не уследить:
надо запускать нужное число копий, перезапускать упавшие, балансировать трафик,
выкатывать новые версии без простоя, масштабировать под нагрузку.

**Kubernetes (K8s)** — это система оркестрации, которая делает всё это
декларативно: ты описываешь **желаемое состояние** (YAML-манифесты), а K8s через
цикл сверки (reconciliation loop) приводит реальность к нему и поддерживает её.

> [!tip] Что сказать на собесе
> «Kubernetes — декларативный оркестратор: я описываю желаемое состояние, а
> контроллеры постоянно сверяют его с фактическим и чинят расхождения.»

## Основные объекты

- **Pod** — минимальная единица развёртывания: один или несколько тесно связанных
  контейнеров с общими сетью и storage. Обычно — один контейнер на под.
- **ReplicaSet** — поддерживает заданное число одинаковых подов.
- **Deployment** — управляет ReplicaSet, добавляет декларативные обновления и
  откаты (rolling update / rollback). На практике работают именно с Deployment.
- **Service** — стабильная сетевая точка доступа к набору подов.
- **ConfigMap** — несекретная конфигурация (переменные, файлы).
- **Secret** — секреты (пароли, токены), хранятся отдельно от конфигурации.
- **Ingress** — HTTP(S)-маршрутизация снаружи в Service (хосты, пути, TLS).
- **Namespace** — логическое разделение ресурсов внутри кластера.

## Что такое Pod

Pod — это обёртка вокруг одного (обычно) или нескольких контейнеров. Контейнеры в
одном поде делят сетевое пространство (один IP, общий localhost) и могут делить
тома. **Поды эфемерны**: при пересоздании под получает новый IP, поэтому
обращаться к подам напрямую по IP нельзя — для этого есть Service.

## Service и label selector

Под живёт недолго и меняет IP, поэтому клиенты ходят не в под, а в **Service**.
Service получает стабильное имя (DNS) и виртуальный IP, а реальные поды-бэкенды
выбирает по **label selector** — он матчит поды, у которых лейблы совпадают с
`selector` сервиса.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api        # выбирает все поды с лейблом app=api
  ports:
    - port: 80
      targetPort: 8080
```

Так связь Service → Pod держится на лейблах, а не на IP. Поды приходят и уходят —
Service автоматически обновляет список эндпоинтов.

## Типы Service

- **ClusterIP** (по умолчанию) — виртуальный IP, доступный только **внутри**
  кластера. Для общения сервисов между собой.
- **NodePort** — открывает порт на каждой ноде; снаружи доступ по `IP_ноды:порт`.
- **LoadBalancer** — заказывает внешний балансировщик у облака и отдаёт внешний IP.

Снаружи HTTP обычно публикуют через **Ingress** поверх ClusterIP-сервисов, а не
вешают LoadBalancer на каждый сервис.

## Liveness и readiness probes

Kubernetes проверяет здоровье контейнеров пробами:

- **liveness** — «жив ли процесс?». Если падает — контейнер **перезапускается**.
- **readiness** — «готов ли принимать трафик?». Если падает — под **убирают из
  эндпоинтов Service** (трафик не идёт), но не перезапускают.

> [!warning] Грабли
> Путать их опасно: если на медленном старте использовать только liveness, K8s
> будет перезапускать ещё не прогревшийся под в цикле. Для готовности — readiness.

## Масштабирование и HPA

Масштабировать приложение горизонтально — значит менять число реплик подов.
Вручную: `kubectl scale deployment api --replicas=5`. Автоматически —
**HorizontalPodAutoscaler (HPA)**: он меняет число реплик по метрике (например,
средний CPU выше целевого → добавить поды).

## Rolling update

Deployment по умолчанию обновляет версию **постепенно**: поднимает новые поды,
ждёт их готовности (readiness), затем гасит старые. Так выкатка идёт **без
простоя**, а при проблеме можно откатиться (`kubectl rollout undo`).

## requests и limits

Под каждый контейнер задают ресурсы:

- **requests** — гарантированный минимум; планировщик использует его, чтобы
  выбрать ноду с достаточными ресурсами.
- **limits** — жёсткий потолок. Превышение CPU → троттлинг; превышение памяти →
  контейнер убивают (OOMKilled).

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"
```

## Итог

- Kubernetes — декларативный оркестратор: описываешь желаемое состояние, он его
  поддерживает.
- Pod — минимальная единица, эфемерна; работают через Deployment.
- Service даёт стабильный адрес и находит поды по label selector.
- Типы Service: ClusterIP (внутри), NodePort, LoadBalancer; снаружи HTTP — через
  Ingress.
- liveness перезапускает, readiness убирает из трафика.
- HPA масштабирует по метрикам; rolling update — выкатка без простоя.
- requests — гарантия и планирование, limits — потолок (OOMKilled при превышении
  памяти).
