# Docker и контейнеризация

Цель урока — за 15 минут разобрать, что такое контейнер, чем он отличается от
виртуалки, как устроены образы и слои, как читать и писать Dockerfile и какие
есть best practices. Простым языком, с прицелом на устные ответы.

## Контейнер vs виртуальная машина

**Виртуальная машина** виртуализирует железо: на гипервизоре крутится полноценная
гостевая ОС со своим ядром. Это тяжело — гигабайты на диске, секунды-минуты на
старт.

**Контейнер** виртуализирует ОС, а не железо. Все контейнеры на хосте делят
**одно ядро Linux**, а изоляция достигается фичами ядра — namespaces (изоляция
процессов, сети, файловой системы) и cgroups (ограничение CPU/памяти).
Контейнер — это, по сути, изолированный процесс. Отсюда лёгкость: мегабайты и
старт за доли секунды.

> [!tip] Что сказать на собесе
> «Контейнер не запускает свою ОС — он использует ядро хоста и изолируется через
> namespaces и cgroups. Поэтому он легче и быстрее виртуалки, но привязан к ядру
> Linux.»

## Образы и слои

**Образ (image)** — это неизменяемый шаблон, из которого запускается контейнер.
Образ состоит из **слоёв (layers)**: каждый слой — это дельта изменений файловой
системы. Слои складываются друг на друга (union filesystem) и доступны только
для чтения. При запуске контейнера сверху добавляется тонкий **writable-слой** —
всё, что контейнер пишет, идёт туда и исчезает при удалении контейнера.

Слои кешируются и переиспользуются между образами. Если два образа основаны на
одном `FROM`, базовые слои хранятся на диске один раз.

## Dockerfile: основные инструкции

```dockerfile
FROM php:8.3-fpm-alpine        # базовый образ
WORKDIR /app                   # рабочая директория
COPY composer.json ./          # копирование файлов в образ
RUN composer install --no-dev  # выполнение команды на этапе сборки
COPY . .                       # копирование остального кода
EXPOSE 9000                    # документирует порт (ничего не публикует)
CMD ["php-fpm"]                # команда по умолчанию при запуске
```

- **`FROM`** — с какого базового образа начинаем.
- **`RUN`** — выполняется во время **сборки**, создаёт новый слой.
- **`COPY`** — копирует файлы из контекста сборки в образ. (`ADD` умеет ещё
  распаковку и URL, но обычно предпочитают `COPY` — он предсказуемее.)
- **`CMD`** — команда по умолчанию при **запуске** контейнера, легко
  переопределяется в `docker run`.
- **`ENTRYPOINT`** — задаёт сам исполняемый файл; аргументы из `CMD`/командной
  строки добавляются к нему.

## CMD vs ENTRYPOINT

Частый вопрос. Коротко:

- `CMD` — это **значение по умолчанию**, которое легко заменить: `docker run img bash`
  полностью заменит `CMD`.
- `ENTRYPOINT` — это **фиксированная точка входа**; то, что передаёшь в
  `docker run`, становится аргументами к ней.
- Частый паттерн: `ENTRYPOINT` — бинарь/скрипт, `CMD` — аргументы по умолчанию.

```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]   # аргументы по умолчанию к nginx
```

## Кеш слоёв и порядок инструкций

Docker кеширует результат каждой инструкции. При повторной сборке слой берётся из
кеша, **пока не изменился ни сам слой, ни любой слой выше него**. Как только один
слой инвалидируется — все следующие пересобираются.

Отсюда главное правило: **сначала копируй то, что меняется редко, потом то, что
меняется часто.** Зависимости (`composer.json`/`go.mod`) копируют и ставят до
копирования исходников, чтобы при правке кода не переустанавливать пакеты.

> [!warning] Грабли
> `COPY . .` в начале Dockerfile ломает кеш: любая правка кода инвалидирует
> установку зависимостей, и они ставятся заново каждую сборку.

## Multi-stage build

Часто для сборки нужны компилятор, dev-зависимости, тулчейн — а в финальном
образе они не нужны. **Multi-stage build** позволяет собрать артефакт в одном
этапе, а в финальный образ скопировать только результат.

```dockerfile
# этап сборки
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN go build -o /app/server ./cmd/server

# финальный образ — только бинарь
FROM alpine:3.20
COPY --from=build /app/server /server
ENTRYPOINT ["/server"]
```

Результат — крошечный образ без компилятора и исходников. Меньше размер, меньше
поверхность атаки.

## .dockerignore, volumes, сети

- **`.dockerignore`** исключает файлы из контекста сборки (`.git`, `vendor`,
  `node_modules`, логи). Это ускоряет сборку и не тащит мусор в образ.
- **Volumes** — способ хранить данные вне эфемерного слоя контейнера. Нужны для
  БД и любого состояния, которое должно пережить пересоздание контейнера.
- **Сети** — Docker создаёт виртуальные сети; контейнеры в одной сети видят друг
  друга по имени сервиса (встроенный DNS). На этом строится `docker-compose`.

## Best practices

- Маленький базовый образ (`alpine`, `-slim`, `distroless`).
- Multi-stage, чтобы не тащить тулчейн в прод.
- Не запускать процесс от **root** — создать непривилегированного пользователя.
- **Один процесс на контейнер** — контейнер живёт, пока жив его главный процесс.
- Порядок инструкций ради кеша; зависимости до кода.
- `.dockerignore`, чтобы контекст был чистым.

## Итог

- Контейнер — изолированный процесс на ядре хоста (namespaces + cgroups), а не
  отдельная ОС, как у VM.
- Образ состоит из read-only слоёв; контейнер добавляет тонкий writable-слой.
- Кеш слоёв: сначала редко меняющееся (зависимости), потом код.
- Multi-stage уменьшает финальный образ и поверхность атаки.
- `CMD` — переопределяемые аргументы по умолчанию, `ENTRYPOINT` — фиксированная
  точка входа.
- Best practices: маленький образ, не root, один процесс, `.dockerignore`.
